# RFC 0004: DOS 커널 구조를 게스트 메모리에 둔다

- 상태: 제안
- 날짜: 2026-11-14
- 범위: `lib/dos_dos.ml`(할당·핸들·EXEC·종료), `lib/dos_state.ml`, `lib/dos_snapshot.ml`, 새 `lib/dos_mcb.ml`·`lib/dos_sft.ml`

## 왜

DOS 프로그램은 DOS가 메모리에 둔 자료 구조를 직접 읽고 고친다. 이 기계에서는 그 구조가 호스트 쪽에만 있다.

| 구조 | 실기 DOS | 이 기계 |
|---|---|---|
| 메모리 블록 | MCB 사슬. 블록마다 앞 문단에 16바이트 머리(`M`/`Z`, 주인 PSP, 크기, 이름) | `t.blocks : (seg * paras) list`. 게스트 메모리에는 머리가 없다 |
| 열린 파일 | SFT(시스템 파일 표) 항목과 PSP 18h의 JFT(핸들 → SFT 번호) | `t.handles : (int, handle) Hashtbl.t`. PSP의 JFT 칸은 비어 있다 |
| 전체 목록 | INT 21h AH=52h가 주는 List of Lists. 첫 MCB, SFT, 장치 사슬, LASTDRIVE | AH=52h가 없다 |

`dos_dos.ml` 머리 주석이 이 선택을 적어 둔다. 「MCB 사슬을 게스트에게 보여주지는 않는다. 사슬을 직접 훑는 프로그램은 이 모델 밖이고, 그때는 조용히 틀리는 대신 할당 실패로 답한다.」

그래서 생기는 일:

- 제 PSP 바로 앞 문단(PSP-1)에서 블록 크기나 이름을 읽는 프로그램은 MCB가 없는 자리를 읽는다.
- RBIL INT 21/AH=26h는 PSP를 따라가는 프로그램에게 둘 중 하나를 보라고 적는다. PSP 첫 두 바이트가 `CD 20`인지, 앞 문단이 그 PSP를 주인으로 하는 MCB인지다. 지금은 앞쪽 검사가 늘 실패한다.
- AH=52h로 첫 MCB를 찾아 사슬을 훑는 프로그램(메모리 관리자, 상주 프로그램, 설치 프로그램)은 돌지 않는다.
- AH=67h(핸들 수 늘리기)는 PSP 32h·34h와 JFT를 고치는 일이다. 지금 구조로는 만들 수 없다.
- #148이 PSP의 다른 칸을 채웠지만 JFT(18h)와 32h·34h는 남겼다. 핸들의 진실이 호스트 표에 있어서, PSP에 쓰면 진실이 둘로 갈린다.

로컬 게임은 삼국지3 하나다. 어느 게임이 이 RFC로 돌기 시작하는지는 잴 수 없다. 목표는 MS-DOS 4.0 원문과 RBIL에 맞춘 COM 테스트로 잰다.

## 목표

1. 할당의 진실은 게스트 메모리의 MCB 사슬 하나다. `t.blocks`, `t.free_base`, `t.free_top`과 EXEC 프레임의 블록 사본을 지운다.
2. 핸들의 진실은 PSP의 JFT와 게스트 메모리의 SFT다. 호스트는 파일 내용(바이트)만 가진다.
3. INT 21h AH=52h가 List of Lists를 준다.
4. 바뀌지 않는 것:
   - 삼국지3의 프레임, 스텝 수, 세이브 해시가 같다. KOEI 로더가 받는 세그먼트가 같아야 한다.
   - 파일 계약(마운트한 파일만 보이고, 닫을 때 마운트 표로 돌아간다)
   - 결정론

## 하지 않는 것

- DPB(드라이브 매개 블록, AH=1Fh·32h), 디스크 버퍼, FCB 표. List of Lists의 이 포인터는 FFFF:FFFF로 둔다. RBIL AH=52h는 이 값이면 쓰지 말라고 적는다.
- UMB(상위 메모리 블록)와 AH=58h AL=02h·03h. #88이 할당 전략을 다룬다.
- CDS(현재 디렉터리 구조). 드라이브가 여럿이 되는 RFC 0003(#146)과 같이 정한다.

## 근거

- MS-DOS 4.0 원문(github.com/microsoft/MS-DOS `v4.0/src`, 2026-11-14에 받음)
  - `INC/ARENA.INC`: MCB. 서명 4Dh(가운데)·5Ah(끝), 주인(0 = 빈 블록), 크기(문단), 예약 3바이트, 이름 8바이트
  - `INC/SF.INC`: SFT 머리(다음 표, 항목 수)와 항목 `sf_entry`. 참조 수, 열기 모드, 속성, 장치 정보 플래그, 시작 클러스터, 시각, 날짜, 크기, 위치, 이름 11바이트, 주인 PSP(`sf_PID`) 등
  - `INC/SYSVAR.INC`: `SysInitVars`(List of Lists 본체). DPB, SFT, CLOCK$, CON, 최대 섹터, 버퍼, CDS, FCB, 블록 장치 수, CDS 수(LASTDRIVE), NUL 장치 머리
  - `DOS/MISC.ASM` `$Dup_PDB`: EXEC 자식은 부모 JFT 20칸을 받는다. 상속하지 않는 파일(`sf_no_inherit`)은 FFh로 바꾼다
- RBIL INT 21/AH=52h(ctyme rb-2983, 표 01627·01628): List of Lists의 칸과 DOS 판마다의 차이, MCB 형식
- RBIL INT 21/AH=26h(표 01378): PSP 32h(JFT 칸 수, 기본 20)·34h(JFT 포인터, 기본 PSP:0018h)

## 설계

### 단계 1: MCB 사슬

- 새 `Dos_mcb` 모듈이 사슬을 읽고 쓴다. 다른 모듈은 `t.mem`의 MCB를 직접 만지지 않는다.

```ocaml
type kind = Middle | Last                  (* 4Dh, 5Ah *)
type owner = Free | Dos | Process of int  (* 0, 8, PSP 세그먼트 *)
type block = { seg : int; kind : kind; owner : owner; paras : int }

val walk : t -> (block list, corrupt) result
```

- 서명이 4Dh·5Ah가 아니거나 블록이 A000h를 넘으면 `Error corrupt`다. AH=48h·49h·4Ah는 에러로 답하고, 고쳐서 이어 가지 않는다.
- 에러 코드는 07h(메모리 제어 블록이 망가졌다)로 잡는다. 이 값은 단계 1에서 RBIL 에러 코드 표(INT 21h AX=5900h)로 확인한다.
- 할당(48h), 풀기(49h), 크기 바꾸기(4Ah), EXEC 적재, 종료, TSR이 모두 사슬을 고친다. 첫 맞는 자리(first fit)는 지금과 같다. 그래서 같은 요청에 같은 세그먼트가 나온다.
- 빈 블록이 붙어 있으면 합친다. 언제 합치는지는 MS-DOS 4.0 `DOS/ALLOC.ASM`을 따른다. 이 파일은 단계 1에서 받아 대조한다.
- MCB 이름(08h, 8바이트)은 EXEC가 프로그램 이름으로 채운다. 8자보다 짧으면 NUL로 끝낸다. RBIL 표 01628의 DOS 4.0+ 설명이다. 확장자를 빼는지는 단계 1에서 `EXEC.ASM`으로 확인한다.
- 스냅숏은 hard cut이다. `t.blocks` 등은 형식에서 빠진다. 사슬은 메모리에 있으니 메모리 사본이 담는다. 옛 형식을 읽는 코드는 만들지 않는다.

### 단계 2: List of Lists와 DOS 데이터

- AH=52h가 ES:BX로 DOS 데이터 세그먼트 안의 List of Lists를 준다.
- 채우는 칸:

| 칸 | 값 |
|---|---|
| -2 | 첫 MCB 세그먼트 |
| 04h | 첫 SFT(단계 3 전에는 FFFF:FFFF) |
| 08h·0Ch | CLOCK$·CON 장치 머리 |
| 10h | 최대 섹터 크기 512 |
| 20h | 블록 장치 수 |
| 21h | LASTDRIVE |
| 22h | NUL 장치 머리 18바이트(포인터가 아니라 머리 자체) |
| 그 밖의 포인터 | FFFF:FFFF |

- 장치 사슬은 NUL → CON → AUX → PRN → CLOCK$ 순이다. 지금 ROM에 있는 EMM 장치 머리(`EMMXXXX0`)를 사슬 어디에 넣을지는 단계 2에서 실기 순서를 확인하고 정한다.

### 단계 3: SFT와 JFT

- SFT는 DOS 데이터 안의 표다. 항목은 DOS 4.0 `sf_entry` 모양이다. 진실인 칸은 참조 수, 열기 모드, 속성, 장치 정보, 크기, 위치, 이름, 주인 PSP다.
- JFT는 PSP 18h의 20칸(또는 34h가 가리키는 표)이다. 값은 SFT 번호이고, FFh는 닫힘이다. 핸들 0-4는 CON·CON·CON·AUX·PRN 항목을 가리킨다. 이 번호 배치는 단계 3에서 MS-DOS 원문으로 확인한다.
- 호스트에는 SFT 번호마다 파일 내용 버퍼 하나만 남는다. 한 이름을 여러 번 열면 지금처럼 버퍼 하나를 같이 쓴다(#35). 위치는 SFT 항목마다 따로다.
- 45h·46h(dup)는 JFT 칸을 복사하고 참조 수를 올린다. 지금 `dup`가 레코드를 같이 쓰는 규칙과 같은 뜻이다.
- EXEC 자식은 JFT 20칸을 받고 참조 수가 오른다. 자식이 끝나면 자식 JFT의 열린 칸을 닫는다(참조 수가 내린다). 지금 `child_exit`가 「자식이 연 핸들만 닫는다」고 하는 규칙을 참조 수가 대신한다.
- AH=67h가 이 단계에서 생긴다. BX가 20보다 크면 MCB 할당으로 표를 받아 JFT를 옮기고 32h·34h를 고친다. 실패할 때의 에러 코드는 단계 3에서 RBIL AH=67h로 정한다.
- 스냅숏은 hard cut이다. `t.handles`가 형식에서 빠진다.

## 단계와 확인

PR 하나는 9파일 이하다. 단계마다 COM 테스트, 일부러 망가뜨리기, 삼국지3 프레임·시나리오로 확인한다.

1. **MCB 사슬**
   → 확인: 48h·49h·4Ah·EXEC·TSR 뒤에 사슬을 훑어 주인·크기·서명을 시험한다. PSP-1이 자기 소유 블록이다. 머리를 망가뜨리면 07h다. 삼국지3 KOEI 로더가 받는 세그먼트가 지금과 같다.
2. **List of Lists**
   → 확인: AH=52h의 -2가 첫 MCB이고, 그 사슬을 따라가면 루트 PSP 블록이 나온다. NUL 머리의 다음 포인터로 CON에 닿는다. 모르는 포인터는 FFFF:FFFF다.
3. **SFT·JFT·67h**
   → 확인: 열기·닫기·dup·EXEC 상속·종료 뒤 JFT 바이트와 SFT 참조 수·위치를 시험한다. 지금의 핸들 테스트(`dos_exec_test`의 상속·종료 시험 등)가 바뀌지 않고 통과한다.

## 결정할 것

1. **DOS 데이터 자리.**
   - A안: 0x0600-0x0FFF 안에 둔다. 루트 COM의 PSP 1000h와 #85의 SDA(0070h)가 그대로다. SFT 항목 수(FILES=)는 이 자리에 맞춰 작아진다.
   - B안: 첫 MCB를 DOS 소유 블록(주인 0008h)으로 두고 그 안에 둔다. RBIL 표 01628은 「DOS 3.1+에서 첫 메모리 블록은 DOS 데이터 세그먼트」라고 적는다. 실기 배치에 가깝다. 루트 PSP가 올라가 삼국지3이 받는 세그먼트가 바뀐다.
   - 이 RFC는 A안을 제안한다. 목표 4(삼국지3 그대로)를 지킬 수 있는 쪽이다.
2. **FILES= 값.** SFT 항목 수다. A안이면 자리가 정한다.
3. **순서.** 단계 1은 할당을 건드리는 열린 PR(#73·#76·#78·#88 등)과 충돌한다. 병합 순서 이슈 #96에서 자리를 정해야 한다. RFC 0003(#146)의 드라이브 단계와 어느 것을 먼저 할지도 정해야 한다.
   - 단계 3은 핸들 표를 고치는 열린 PR(#126·#127·#129·#130)이 병합된 뒤에 한다. 그 PR들이 정한 동작(표준 핸들 0-4, 42h 32비트 위치, 3Dh 접근 모드와 상속 비트)을 SFT·JFT로 옮기는 일이 된다.

## 위험

- 단계 1·3은 지금 진실을 가진 호스트 표를 지운다. 한 PR 안에서 옛 표와 새 구조가 같이 있으면 둘이 어긋난다. 그래서 단계마다 옛 표를 같은 PR에서 지운다(hard cut).
- 게스트가 MCB나 SFT를 망가뜨리면 지금은 영향이 없던 일이 할당·파일 실패가 된다. 실기와 같은 동작이다. 망가진 구조는 에러로 끝내고, 고쳐서 이어 가지 않는다.
- 사슬을 훑는 비용이 할당마다 든다. 블록 수는 많아야 수십 개다. 단계 1에서 삼국지3 30M 스텝의 user 시간을 main과 비교한다.
