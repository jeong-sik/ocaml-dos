# RFC 0001: 80386 실모드

- 상태: 제안
- 날짜: 2026-11-13
- 범위: `lib/cpu86*.ml`, `test/cpu86_sst*.ml`, `bin/dosboot.ml` 의 CPU 선택

## 왜

이 기계의 CPU 는 8086, 186, 286 이다. 286 은 SingleStepTests/80286 실모드
147만 8천 건 중 6 건만 다르다(#59).

386 을 요구하는 DOS 게임은 이 기계에서 돌지 않는다. 이런 게임은 둘로
나뉜다.

1. 실모드에서 386 명령을 쓰는 게임. 32 비트 레지스터, `66h`·`67h` 접두,
   FS·GS, `0Fh` 확장 명령을 쓴다.
2. DOS 익스텐더(DOS/4GW 등)로 보호 모드에 들어가는 게임.

이 RFC 는 1 만 다룬다. 2 는 보호 모드, 디스크립터 표, XMS·VCPI·DPMI 가
필요하고, 1 을 디딤돌로 쓴다. 따로 RFC 를 쓴다.

로컬 게임은 삼국지3 하나라, 어느 게임이 이 단계로 돌기 시작하는지는 잴 수
없다. 그래서 목표를 실칩 데이터로 잰다.

## 목표

- `Cpu86.model` 에 `I80386` 을 더한다.
- SingleStepTests/80386 `v1_ex_real_mode` 를 돌려 실패를 baseline 파일에
  사유와 함께 남긴다. 처음 목표는 286 과 같다: 사유 없는 실패 0 건.
- 8086·186·286 은 바뀌지 않는다.
  - 286 스위트 결과가 지금과 같다(실패 6 건, 같은 해시).
  - 286 데이터의 초기 상태를 `I8086` 으로 이전·새 코드에 돌린 끝 상태가
    147만 8천 건 모두 같다(#59 에서 쓴 방법).
  - 삼국지3 시나리오의 스텝 수와 세이브가 같다.
- 속도: 삼국지3 30M 스텝(release, `--cache=disabled` 새 빌드, 3 회) user
  시간이 286 경로에서 3% 안으로 는다.

## 데이터

[SingleStepTests/80386](https://github.com/SingleStepTests/80386) README
(2026-11-13 확인):
- Intel 386EX(KU80C386EX33)에서 뽑았다. 데이터 버스가 16 비트라 사이클
  수는 386DX 와 다르다. 이 기계는 사이클을 비교하지 않으니 상관없다.
- `v1_ex_real_mode`: MOO 파일 941 개, 약 576MB.
  - 557 개가 `66h`·`67h` 접두로 시작한다. 286 에 없는 32 비트 형태다.
  - 59 개가 `0Fh` 로 시작한다. `66h`·`67h` 뒤에 `0Fh` 가 오는 것이 80 개 더 있다.
- 주소선은 24 개만 잡았다(16MB).
- 문제 있는 테스트는 `revocation_list.txt` 에 해시로 올라온다. 러너는 이
  해시를 건너뛴다.
- 형식은 286 과 같은 MOO 라 `test/moo.ml` 을 그대로 쓴다.

데이터는 저장소에 넣지 않는다. 286 처럼 디렉터리를 환경 변수로 받고, 없으면
건너뛴다.

## 386 이 실모드에서 달라지는 것

Intel 80386 Programmer's Reference Manual(1986) 기준이다.

| 영역 | 내용 |
|---|---|
| 레지스터 | EAX…EDI, EIP 의 상위 16 비트. FS·GS |
| 접두 | `66h` 피연산자 크기, `67h` 주소 크기. 실모드 기본은 16 비트 |
| 주소 | 32 비트 modrm 과 SIB. 오프셋이 FFFFh 를 넘으면 INT 13, 스택 세그먼트면 INT 12 |
| 명령 길이 | 15 바이트를 넘으면 INT 13 (286 은 10 바이트) |
| `0Fh` 확장 | Jcc rel16/32, SETcc, MOVZX·MOVSX, BT·BTS·BTR·BTC, BSF·BSR, SHLD·SHRD, IMUL r,r/m, LFS·LGS·LSS, PUSH·POP FS·GS, MOV CRn·DRn·TRn |
| 32 비트 형태 | PUSHAD·POPAD, CWDE·CDQ, 문자열 명령의 ESI·EDI·ECX, JECXZ, LOOP 의 ECX |
| FLAGS | 실모드에서 비트 12-14(IOPL, NT)를 쓸 수 있다. 286 은 늘 0, 8086 은 늘 1 이다. 게임의 CPU 판별이 이 차이를 본다 |

## 설계

### 0 단계: `cpu86.ml` 나누기

`lib/cpu86.ml` 은 1,451 줄이고 `step` 하나가 1,000 줄이다(404-1416 행, #59
기준). 386 을 그대로 얹으면 두 배가 된다.

- `step` 안의 지역 함수(`bad`, `do_int`, `alu_group`, `string_op` 등)를 명령
  하나의 문맥(접두, 시작 IP, 결함 처리)을 받는 최상위 함수로 올린다.
- 모듈을 AST 경계로 나눈다: 상태·레지스터·플래그, 디코드(접두·modrm·주소),
  ALU, 문자열, 결함, `step` 디스패치.
- 이 단계는 동작을 바꾸지 않는다. 확인은 위 「목표」의 8086·286 항목 셋과
  속도다.
- 지역 함수가 레지스터를 잡는 클로저라면 `step` 마다 할당될 수 있다. 올리면
  오히려 빨라질 수 있다. 재서 PR 에 적는다.

### 1 단계: 레지스터

두 방법을 재서 고른다.

| 방법 | 장점 | 단점 |
|---|---|---|
| A. `regs` 를 32 비트로 두고 16 비트 쓰기가 상위 반을 지킨다 | 32 비트 명령이 단순하다 | 모든 모델의 16 비트 쓰기에 and·or 가 붙는다 |
| B. 상위 반을 `regs_hi` 로 따로 둔다. `I80386` 만 쓴다 | 8086·186·286 경로가 그대로다 | 32 비트 읽기·쓰기마다 두 칸을 합치고 나눈다 |

A 의 286 경로 비용이 1% 안이면 A, 아니면 B 다.
`segs` 는 6 칸(ES CS SS DS FS GS)으로 늘린다. FS·GS 는 `I80386` 에서만 디코드한다.
다른 모델에서 `64h`·`65h` 와 `0F A0` 등은 지금처럼 다룬다.

### 2 단계: 접두와 폭

- 지금 ALU 는 `width` 를 8·16 으로 받는다. 32 를 더한다.
- `66h`·`67h` 는 명령마다 상태로 들고 다닌다. `I80386` 이 아닌 모델에서는
  지금 동작 그대로다.
- 주소 크기가 32 이면 modrm·SIB 로 디코드하고, 오프셋이 FFFFh 를 넘으면
  #59 의 결함 모델로 INT 13·12 를 낸다.

### 3 단계: `0Fh` 확장

위 표의 명령을 데이터 파일 단위로 하나씩 더한다. 파일마다 실패 수를 PR 에
적는다. MOV CRn 은 CR0 의 PE 비트를 켜려 하면 `Unsupported` 로 멈춘다. 보호
모드는 이 RFC 범위 밖이다.

### 4 단계: 기계에서 고르기

- `Dos_machine` 의 기본 CPU 는 286 으로 둔다. 기본을 바꾸면 모든 게임의 CPU
  판별 결과가 바뀐다. 삼국지3 도 다른 코드 경로를 탈 수 있다.
- `dosboot --cpu 386` 처럼 고르게 한다. 스냅숏에 모델을 넣는다.
- 기본을 386 으로 바꾸는 일은 386 을 요구하는 게임으로 확인한 뒤 따로 정한다.

## 범위 밖

- 보호 모드, 페이징, V86, 디스크립터 표
- XMS·VCPI·DPMI, DOS 익스텐더 → 다음 RFC
- 8087·387 FPU
- 486 명령(BSWAP, XADD, CMPXCHG 등)과 EFLAGS AC 비트
- 사이클 정확도

## 위험

- 0 단계가 커서 다른 CPU PR(#56, #59)과 충돌한다. #59 가 병합된 뒤 시작한다.
- 386EX 는 386DX 와 몇 가지가 다를 수 있다. 다른 결과가 나오면 baseline 에
  사유를 적고 Intel 매뉴얼과 견준다.
- 데이터 576MB 는 CI 에 없다. 로컬에서만 돈다. CI 에 넣으려면 내려받는 단계와
  캐시가 필요하다.

## 정할 것

1. 이 저장소의 RFC 자리. 이 RFC 는 `docs/rfc/` 를 제안한다.
2. 1 단계 레지스터 저장 방식(A·B). 측정으로 정한다.
3. CI 에서 386 스위트를 돌릴지.

## 확인 방법 요약

| 0 | 286 스위트 같은 결과, 8086 147만 8천 건 같음, 삼국지3 같음, 속도 ±3% |
